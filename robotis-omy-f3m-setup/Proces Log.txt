============= up to 16 October 2026
Training and inference of the Robotis omy-3fm is now under control.

- Setup 	- new HCR setup (grey/red)
- Robot		- Robotis OMY-3FR runs Open_manipulator docker 4.1.0 (06 November 2025), newest version is 5.1.4 of 16 October 2026
- Software	- Robotis OpenManipulator (docker image 5.1.1 arm64 Hub manifest sha256:f925118982cb) and Physical AI server (docker image 1.0.0 + edits to run FastRTPS because the robot still runs on RTPS)
- Training 	- (Tech specs see below) A large variety of parameters was used in the trainings (different sizes of green blocks, different positions and sometimes releasing the blocks to perform a correction action). The approach path was also not necessarily performed accurately, the focus was mainly on a targeted pick-up action. The orientation of the block relative to the robot gripper was also taken into account.
- Results	- In practically all trainings you see a very hesitant pick-up action where the gripper keeps hovering above the block/object and does not really know when the robot should grasp. When waiting longer for the action (+15/30s) the robot sometimes manages to pick up the block. After that, about half of the time the block is released again and the action starts over from the beginning.

Notes on the trainings:
- All runs: 20k steps, checkpoint every 5k steps. Unless stated otherwise trained on the HCR HP ZBook Fury G1i (RTX PRO 5000, 24 GB).
- pi0: lerobot/pi0_old, only the action expert is trained (train_expert_only). On the ZBook only batch 4 fits in memory.
- (ailab) = trained on the ailab server (RTX PRO 6000, 96 GB). bs64accum = batch 64 as 2 x 32 with gradient accumulation.
- groot_n17: NVIDIA GR00T N1.7, trained with Isaac-GR00T (bf16 backbone + 8-bit optimizer to fit in 24 GB). Only on the laptop, removed from the Jetson.
- smolvla_block_placing_II_combined and smolvla_block_placing_II_pos1-3 are trained on the same dataset (pos 1-3).
- Episodes per position in Block placing II: pos 1: 40, pos 2: 14, pos 3: 15, pos 4: 20, pos 5: 20, pos 6: 19.

Training:
cd ~/Developer/robotis/physical_ai_tools/lerobot

TOKENIZERS_PARALLELISM=false
systemd-inhibit --what=sleep:idle:handle-lid-switch --who=lerobot --why="SmolVLA training"

.venv/bin/python -m lerobot.scripts.train --policy.path=lerobot/smolvla_base --policy.push_to_hub=false --policy.device=cuda --dataset.repo_id="avanssmingaars/omy_f3m_[DATASET_NAME]" --dataset.root="/home/simon/Developer/robotis_data/avanssmingaars/omy_f3m_[DATASET_NAME]" --wandb.enable=false --batch_size=32 --steps=20000 --policy.scheduler_decay_steps=20000 --save_freq=5000 --num_workers=4 --output_dir=outputs/train/[TRAINING_OUTPUT_NAME] --job_name=[TRAINING_OUTPUT_NAME]_bs32_decay20k

LeRobot won’t start if the output folder already exists.
To continue an interrupted run from its last checkpoint:

.venv/bin/python -m lerobot.scripts.train --config_path=outputs/train/[TRAINING_OUTPUT_NAME]/checkpoints/last/pretrained_model/train_config.json --resume=true

For a run that keeps going after you close the terminal, I started it with setsid nohup ... > outputs/train/<name>.log 2>&1 < /dev/null & disown around the same command.
The full script I used is saved at outputs/train/chain_single_task.sh.

Put the output in /home/rens/Code/robotis-omy/datasets and then in the deeplink (in the git repo, so you always have a directory outside the git repo in case of data loss
on a possible hard reset of the repo)

Run the policy in Robotis Inference.

============= 16 October 2026

The current policies turned out not to get higher than a 10% success rate, and only with a far too long execution time > 10x the recording time. After research into better SmolVLA finetuning techniques:
https://medium.com/@rahil.lasne/why-your-robot-policy-doesnt-work-and-how-to-find-out-in-30-seconds-43d3beb65888
https://physicalailab.io/en/smolvla-lerobot-fine-tuning/
it was decided to make the following changes:
- Use an extra camera (already done in the last 2 trainings) and this time aimed a bit higher so the gripper of the robot is better in view
- First start with an unambiguous task with little variation in execution and object. Chose the dark green duplo block and 1 position for picking up and placing.
- 1 Task (instead of multiple subtasks)
- 50 Episodes of 15s (same as previous trainings)
- 10% correction movements (dropping the block, picking it up again and placing it in the red bin)
- Dataset name: Block placing
- policy name: smolvla_block_placing_bs32_decay20k
- Instruction: "Pickup green block and place into red bin"

============= 6 November 2026

Collected new data for positions 2-6 (dataset Block placing II, pos 2: 14, pos 3: 15, pos 4: 20, pos 5: 20, pos 6: 19 episodes) and trained new policies on combined positions (SmolVLA pos 1-3, pos 1-5 and pos 1-6; pi0 pos 1-5 and pos 1-6 is training on ailab).
- Positions 1-5 are in the standard 0 degree orientation of the end effector
- Position 6 is in the -90 degree orientation of the end effector
- Conclusion: it seems like training more specific positions with 15 episodes (so not random) is generalising the position picking, and even some unknown positions are being grasped (data in the spreadsheet policy-results.ods will follow)
- Positions outside the boundary of the known positions are still not successful
- Next test: add more positions on the grid and see if the model generalises even more
- pi0 vs SmolVLA: at first SmolVLA seems to be performing better (pos 1: SmolVLA 95% success at 5K steps vs pi0 at most 20%), but pi0 with multiple positions is still being tested
